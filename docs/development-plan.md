# GP07 Unitypackage キャラクタービューア開発方針

更新日：2026-10-16 UTC  
文書版：0.1  
作成：dot  
状態：初期方針書。初版の限定試作を実装済み。現在の対応条件と検証結果は [対応プロファイル](supported-profile.md) と [検証記録](validation.md) を参照。以下の広い M1 条件すべての完了を意味しない。

## 結論

Unity を起動せず、手元の `.unitypackage` に含まれるキャラクターをブラウザ内で確認するビューアを小さく試作する。最初は lilToon の基本色・単純なトゥーン影・輪郭線に対象を絞り、元の見た目をどこまで保てるか検証する。

原画面との完全一致を約束しない。通常の PBR 表示だけで完了とせず、対応したマテリアル情報と近似・未対応箇所を画面に出す。まず再配布可能な自作テスト素材で取り込みから表示までを確認し、同一モデルの正当な Unity 基準画像が手に入った段階で再現性を評価する。

## 目的と未決定事項

- 想定利用場面：Unity を立ち上げる前に、入手済みキャラクターの形状・色・素材割り当て・基本的な見え方を確認する。
- 利用者仮説：Unity 向けキャラクター素材を扱う制作者。顧客検証と購入意思の確認は未実施。
- 入力：ユーザーがローカルで選択した単一の `.unitypackage`。
- 初期出力：回転・ズームできる静止 3D プレビューと、対応状況・警告の一覧。
- 長期方向：Unity 由来と Blender 由来の素材を同じ確認画面で扱う。形式別の入力処理を分け、共通のシーン・マテリアル表現へ変換する。
- 収益モデル、販売方法、価格、予算上限、納期、公開先、対応機器の最終範囲：未決定。
- 初期文書・初期コードの公開と、動作するサービスの公開・費用発生・第三者素材の共有は別に扱う。

## 調査結果と採用理由

確認日はいずれも 2026-10-16。既存製品の記述は提供元の公表内容であり、実際のファイルを使った検証結果ではない。

### ブラウザでの先行事例

[extractunitypackage.com の viewer 説明](https://extractunitypackage.com/unitypackage-viewer)は、ブラウザ内でパッケージを処理し、対応する FBX・Prefab・シーン・テクスチャを確認できると説明している。マテリアルは可能な範囲で標準 PBR に変換し、カスタムシェーダーや Unity の実行ロジックは再現しない。アニメーションプレビューも現時点の説明では非対応。

この事例から、単なるパッケージ展開と 3D 表示には既存の選択肢がある。一方、lilToon の見え方を重点的に保つ余地はあると考える。ただし差別化の大きさや需要は仮説であり、競合より高精度・高速とはまだ言えない。

### lilToon

[lilToon の LICENSE](https://github.com/lilxyzw/lilToon/blob/master/LICENSE)は MIT。利用するコードまたは実質的部分に必要な著作権表示と許諾表示を残す。MIT の対象を、Unity 側の依存コード、同梱の第三者コード、モデル・テクスチャなどへ自動的に拡張して解釈しない。

[公式リポジトリ](https://github.com/lilxyzw/lilToon)は Unity への導入を前提とする。ブラウザ側では Unity 用コードをそのまま実行せず、対象版を固定して必要な描画仕様を確認し、限定的な互換描画を構成する。採用版・参照ファイル・改変箇所・ライセンスを実装時に記録する。

### Blender 経由の先行事例

[utagestudio/unitypackage_loader](https://github.com/utagestudio/unitypackage_loader)は、Unity を起動せず Blender にモデル・マテリアル・テクスチャを取り込むアドオンで、リポジトリの表示は GPL-3.0。ブラウザ製品とは利用環境が異なる。

本試作では機能範囲と制約の調査対象にとどめ、コードをコピー・移植・依存導入しない。将来採用する場合は配布形態とライセンス条件を別途検討する。単に別プロセスにすれば問題がないといった法的保証はしない。

### 比較した選択肢

1. 既存 viewer を使う：すぐに構造や PBR プレビューを確認できる可能性がある。lilToon 再現は公表範囲にない。
2. Blender importer を使う：制作工程の調査対象として有用。Blender の起動が必要で、今回のブラウザ単体体験とは異なる。
3. 限定したブラウザ互換ビューアを作る：見た目の再現に投資できるが、形式差・シェーダー差を保守する負担がある。

推奨は 3 の小さな試作。まず一つのサポート対象を最後まで表示し、実用価値がなければ範囲修正または停止する。

## 最初の対応範囲

### 対応するもの

- gzip/tar ベースのパッケージから、GUID・pathname・asset・asset.meta の対応を検査して読み取る。
- サポート対象として明記したテキスト形式の `.mat`・`.meta` と、単純な Prefab の参照を読み取る。
- 一つの自己完結した FBX と、その素材スロット、パッケージ内の PNG/JPEG テクスチャを結ぶ。
- 最初のフィクスチャは静的メッシュと固定姿勢。キャラクターのスキニング・骨参照の一般対応は次段階で検証する。
- lilToon 基本色、メインテクスチャ、単段のトゥーン影、基本輪郭線を限定実装する。
- カメラ回転・ズーム・リセット、明示的な読み込み状態、警告、クリア、再読み込み。

### 最初は対応しないもの

- Unity エディター、Unity シーン全体、ShaderLab/HLSL の汎用実行。
- C#・DLL・Editor 拡張・任意 JavaScript の実行。
- 動的骨、物理、VRChat SDK、表情メニュー、Animator、アニメーション再生。
- Prefab Variant、複雑なネスト／override、全 FBX バージョン、全 Unity importer 挙動。
- 透過・多段影・マットキャップ・リムライト・ノーマルマップ・発光・特殊マスクなど lilToon の完全互換。
- `.blend` の直接読み込み、任意 Blender ノードの再現、GLB エクスポート、クラウド変換、アカウント、決済。

未対応機能を持つ材質は、検出できた未対応項目と代替表示を警告する。影や輪郭線を描けたことを「lilToon 完全対応」と表示しない。未知のシェーダーは明確な代替材質を使い、無言で互換扱いしない。

## 技術構成の方針

処理を、入力検査 → 安全な展開 → アセット索引 → 参照解決 → シーン構築 → 材質変換 → 描画、に分割する。画面と解析処理を分離し、重い解析は Worker でキャンセルできる形にする。ブラウザ描画エンジン、FBX ローダー、tar/gzip・YAML パーサーは実装環境と依存物の権利を確認してから選定・固定する。

参照は名前の類似だけで決めず、GUID と fileID を保持する。FBX 内の subasset と Unity importer の fileID の対応を解けない場合は、曖昧な素材を勝手に割り当てず警告する。単純なテスト素材で成功しても一般的な Unity importer 互換とはみなさない。

中間表現には、元の GUID/fileID、ノード・メッシュ・素材スロット・テクスチャ、変換の出典、適用した近似、未対応項目を持たせる。Unity のテキスト形式や meta の前提は公式資料で確認し、対応 Unity 版と試験素材の条件を記録する。

描画では色空間、テクスチャの向き・UV・tiling/offset、座標系・単位、面の向き、法線、深度・カリング、ライト・カメラ・トーンマッピングを明示する。輪郭線方式は候補を小さく試し、幅の単位と Unity 側との差を記録する。lilToon のプロパティ名・既定値は固定した参照版で実装前に検証する。

## 安全とローカル処理

- パッケージの内容をサーバー、解析サービス、計測サービスへ送信しない。素材名・パス・画像・ハッシュも外部テレメトリーへ含めない。
- 初期版では永続保存を行わず、ブラウザ内メモリーで処理する。クリア時に Worker、Blob URL、CPU/GPU リソースを解放する。
- アプリ自体の配信通信と、素材データの処理を区別する。依存物を同梱し、素材解析中の外部 fetch・画像 URL・外部参照解決を禁止する。ブラウザローカルという設計だけで安全性確認済みとはしない。
- tar entry と pathname の両方を検査する。絶対パス、ドライブ／UNC、`..`、NUL、重複／正規化衝突、シンボリックリンク・ハードリンク、デバイス等の特殊 entry を拒否する。展開は仮想ファイル集合とし、OS のパスへ直接書き出さない。
- ファイル拡張子だけを信頼せず、ヘッダー・長さ・チェックサム・境界を検査する。破損データや重複 GUID を黙って補正しない。
- 圧縮サイズ、展開総量、entry 数、単体サイズ、画像デコード後の画素数、頂点／インデックス数、解析時間に明示上限を設ける。全量展開してから判定せず、ストリーム処理中にも予算を減算する。
- M1 の暫定上限案：入力 32 MiB、展開合計 128 MiB、2,000 entry、単体 32 MiB、画像 4096×4096 以下かつ合計 32M pixels、頂点合計 500,000、解析 15 秒。これは製品保証や実測性能ではない。対象環境の試験後に理由を残して調整する。
- YAML のカスタムタグ実行を禁止し、alias・深さ・ノード数を制限する。ファイル名やエラー表示はテキストとして扱い、HTML として挿入しない。
- パッケージ内のスクリプト、シェーダーコード、外部 URL は実行しない。必要なデータのみ、既知のスキーマとして解析する。

## 最初のマイルストーン M1

### 確かめる仮説

自作の小さな unitypackage フィクスチャから、参照で結ばれたメッシュ・色・テクスチャを安全に表示し、限定トゥーン描画と未対応警告を一つの画面で確認できる。

### 成果物

1. ローカル起動できる最小ビューア。デモ読み込みと `.unitypackage` 選択を分けて表示する。
2. 自作の小さなフィクスチャ。単純 FBX、PNG、テキスト材質、最小 Prefab、meta と GUID の関係を含め、生成方法と権利を記録する。
3. 安全性・参照解決・画面操作のテストと、再現用手順。
4. 実物スクリーンショット、ログ、試験環境、対象 commit、対応／非対応一覧。
5. 依存物・素材のライセンス一覧と、使用した lilToon の参照版／表示条件。

描画だけのデモが先にできた場合は「描画実験」とする。パッケージ取り込み、参照解決、安全性試験まで揃わなければ M1 完了とはしない。

### 合格条件

- 自作フィクスチャを、取り込みから回転・ズーム・リセットまで実画面で操作できる。
- 基本色・影・輪郭線の各設定変更が意図した描画差になる。固定カメラ／ライトで証拠を残す。
- GUID と fileID の対応がフィクスチャの期待値と一致する。欠落・曖昧な参照は診断に出る。
- 未知シェーダー、未対応プロパティ、壊れた圧縮データ、危険パス、重複、上限超過が安全に扱われる。
- 空状態、読み込み中、失敗、キャンセル、連続ファイル選択、クリア後の再読み込みを確認する。古い解析結果で新しい選択が上書きされない。
- ブラウザのネットワーク記録で、素材処理時の素材データ送信がないことを確認する。ログに私有素材を含めない。
- lint、型検査、単体テスト、結合テスト、ビルドを分けて実施し、実施できなかったものは未確認と記録する。

### 中止または保留条件

安全な展開上限を強制できない、参照の曖昧さで誤表示を検知できない、必要な依存物の利用条件を満たせない場合は、該当機能を止める。機能削減で進める場合は変更理由と判定基準を残す。費用・公開・外部サービスが必要になった場合は承認を得るまでその工程を保留する。

## 見た目の再現性を評価する次段階

M1 は機能試験であり、原モデルの外観保持を証明しない。現在、同じモデル・同じ設定の Unity 基準画像は未入手。比較欄は未確認とし、別モデルの画像や広告画像を代用して一致率を出さない。

M2 で、利用・試験が許可された一体の実モデルと同一設定の基準を用意する。モデルとテクスチャの版、Unity・lilToon・レンダーパイプライン、姿勢、カメラ、ライト、背景、解像度、色空間を揃える。Unity 基準画像の作成が必要なら、利用可能な Unity 環境と実行範囲を確認する。ビューア通常利用時に Unity を必要としない方針は維持する。

比較項目は、色、素材割り当て、シルエット、影境界、輪郭線、髪や目の表示など。画像差分と目視確認を併用し、条件差を差分に混ぜない。合格閾値は基準条件と対象機能が決まった時点で、結果を見る前に固定する。基準が揃わなければ「Unity 同等」や「再現率」を宣言しない。

M3 以降の候補は、スキンドメッシュと固定姿勢、透過、追加 lilToon 機能、Prefab Variant、Blender 由来の glTF/GLB 入力。各段階を実物で評価してから拡張し、今回の着手で一括実装しない。
